Глобальний State Management

Еволюція стану в React

Коли useState + Context недостатньо

Context API — чудовий інструмент, але має обмеження:

  • Будь-яка зміна value → re-render ВСІХ consumers, навіть якщо вони використовують лише одне поле;
  • Немає селективної підписки — не можна підписатися лише на user.name, ігноруючи user.role;
  • Немає middleware — немає devtools, persistence, time-travel;
  • Немає async actions — складно робити складні flows;
  • Provider wrapper — треба обгортати дерево.

Коли потрібен state manager:

  • Кілька незалежних «слайсів» стану (cart, user, theme, filters);
  • Часті оновлення + багато компонентів-споживачів;
  • Потрібна persistence (localStorage sync);
  • Потрібні DevTools для відлагодження;
  • Складні async flows.

State Management — огляд інструментів

Zustand — Client State

Zustand — архітектура

Zustand — базовий store

// store/useStore.ts
import { create } from "zustand";

type Store = {
  user: User | null;
  cart: CartItem[];
  theme: string;
  // actions
  login: (user: User) => void;
  logout: () => void;
  addToCart: (item: CartItem) => void;
  setTheme: (theme: string) => void;
};

export const useStore = create<Store>((set, get) => ({
  user: null,
  cart: [],
  theme: "light",

  login: (user) => set({ user }),
  logout: () => set({ user: null }),
  addToCart: (item) => set((state) => ({
    cart: [...state.cart, item]
  })),
  setTheme: (theme) => set({ theme }),
}));

Zustand — мінімалістичний state manager (~1KB).

Особливості:

  • Store — звичайний hook useStore;
  • set() — оновлення стану (як useState, але глобально);
  • get() — читання поточного стану;
  • Без Provider — store живе поза деревом компонентів;
  • State + actions в одному об'єкті.

Встановлення: npm install zustand

Zustand — селективна підписка

// ✅ Selective subscription
function Navbar() {
  // only re-renders when user changes
  const user = useStore(s => s.user);
  return <nav>Hello, {user?.name}</nav>;
}

function CartIcon() {
  // only re-renders when cart.length changes
  const count = useStore(s => s.cart.length);
  return <span>Cart ({count})</span>;
}

// ✅ Multiple fields
const { user, theme } = useStore(s => ({
  user: s.user, theme: s.theme
}));

// ✅ Actions (stable references)
const addToCart = useStore(s => s.addToCart);

// ✅ Get without subscribe
const items = useStore.getState().cart;

Селектор — функція (state) => value.

Перевага над Context:

  • Компонент не перерендериться, якщо змінюється поле, яке він не читає;
  • Можна повернути об'єкт з кількох полів (з shallow comparator);
  • Actions стабільні (не треба useCallback);
  • getState() — читання без підписки (в event handlers).

Shallow compare для об'єктів:

import { shallow } from "zustand/shallow"
useStore(selector, shallow)

Zustand — async actions

export const useStore = create<Store>((set, get) => ({
  user: null,
  loading: false,
  error: null,

  // Async action built-in!
  login: async (email: string, password: string) => {
    set({ loading: true, error: null });
    try {
      const { user, token } = await authApi.login(email, password);
      localStorage.setItem("token", token);
      set({ user, loading: false });
    } catch (e) {
      set({ error: e.message, loading: false });
    }
  },

  // Read current state with get()
  checkout: async () => {
    const cart = get().cart;
    await ordersApi.create({ items: cart });
    set({ cart: [] });
  },
}));

Async в Zustand — просто async функція в store.

Без thunk/saga — як у Redux.

get() — читання стану без підписки (всередині actions).

Виклик з компонента:

const login = useStore(s => s.login);
const loading = useStore(s => s.loading);

const handleSubmit = async () => {
  await login(email, password);
  navigate("/dashboard");
};

Компонент не містить логіки — лише викликає action.

Zustand — slices (модульний store)

// store/userSlice.ts
export const createUserSlice = (set, get) => ({
  user: null,
  login: async (email, pwd) => { ... },
  logout: () => set({ user: null }),
});

// store/cartSlice.ts
export const createCartSlice = (set, get) => ({
  cart: [],
  addToCart: (item) => set(s => ({
    cart: [...s.cart, item]
  })),
  removeFromCart: (id) => set(s => ({
    cart: s.cart.filter(i => i.id !== id)
  })),

// store/index.ts — combine slices
export const useStore = create({
  ...createUserSlice,
  ...createCartSlice,

Slices патерн — розділення store на логічні частини.

Переваги:

  • Кожен slice — окремий файл;
  • Легко знайти та підтримувати;
  • Композиція через spread;
  • Можна тестувати окремо;
  • Slices можуть викликати один одного через get().

Аналог — Redux Toolkit slices, але без boilerplate.

Server State — TanStack Query

Client State vs Server State

Чому server state — інший?

Server state має унікальні властивості, яких немає у client state:

  • Може бути застарілим — інший користувач змінив дані на сервері, ваш кеш — outdated;
  • Спільний — кілька компонентів використовують ті самі дані;
  • Потребує invalidation — після мутації треба оновити кеш;
  • Потребує cache — щоб не refetch при кожному mount;
  • Потребує retry — мережа може бути нестабільною;
  • Потребує optimistic updates — для швидкого UX;
  • Потребує pagination / infinite scroll — для великих списків.

useState + useEffect не рішення для server state. TanStack Query автоматизує все це.

TanStack Query — як це працює

TanStack Query — cache lifecycle

Ручний CRUD vs TanStack Query

// Ручний (useState + useEffect)
const [users, setUsers] = useState()
const [loading, setLoading] = useState()
const [error, setError] = useState()

useEffect(() => {
  fetch(...).then(setUsers)
}, [])
  • ❌ no cache (refetch on every mount)
  • ❌ no dedup (2 components = 2 fetch)
  • ❌ no refetch on focus/reconnect
  • ❌ manual refetch after mutation
  • ❌ no pagination/infinite helpers
  • ❌ race conditions to handle
  • ❌ no prefetch, no optimistic

~50 lines of boilerplate per query

// TanStack Query
const { data, isLoading, error }
  = useQuery({
    queryKey: ["users"],
    queryFn: () => api.getUsers()
  })
  • ✅ automatic cache + dedup
  • ✅ refetch on focus/reconnect
  • ✅ invalidation after mutation
  • ✅ pagination, infinite scroll
  • ✅ prefetch, optimistic updates
  • ✅ retry, rollback on error
  • ✅ DevTools, no race conditions

~3 lines of code per query
useMutation + invalidateQueries

TanStack Query — useQuery

import { useQuery } from "@tanstack/react-query";

function UserList() {
  const {
    data,        // User[] | undefined
    isLoading,   // boolean (first load)
    isFetching,  // boolean (any fetch)
    isError,     // boolean
    error,       // Error | null
    refetch,     // () => Promise
  } = useQuery({
    queryKey: ["users"],
    queryFn: () => usersApi.list(),
    staleTime: 60 * 1000,  // 60s fresh
    refetchOnWindowFocus: true,
  });

  if (isLoading) return <Spinner />;
  if (isError) return <ErrorView error={error} onRetry={refetch} />;

  return (
    <ul>
      {data.map(u => <li key={u.id}>{u.name}</li>)}
    </ul>
  );
}

useQuery — хук для читання server state.

queryKey — унікальний ключ для кешу (як ["users"], ["user", "42"], ["products", {page: 2}]).

queryFn — функція, що повертає Promise (fetcher).

Автоматично:

  • кешує результат;
  • дедуплікує паралельні запити;
  • refetch на focus/reconnect;
  • retry при помилці (3 рази).

isLoading — перший load (даних ще немає). isFetching — будь-який fetch (включає background refetch).

TanStack Query — useMutation

TanStack Query — useMutation код

import {
  useMutation, useQueryClient
} from "@tanstack/react-query";

function DeleteUser({ id }) {
  const queryClient = useQueryClient();

  const mutation = useMutation({
    mutationFn: () => usersApi.delete(id),

    // Optimistic update
    onMutate: async () => {
      await queryClient.cancelQueries({ queryKey: ["users"] });
      const prev = queryClient.getQueryData(["users"]);
      queryClient.setQueryData(["users"], old =>
        old?.filter(u => u.id !== id));
      return { prev };
    },

    onError: (_err, _vars, ctx) => {
      queryClient.setQueryData(["users"], ctx.prev);
    },

    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: ["users"] });
    },
  });

  return <button onClick={() => mutation.mutate()}
    disabled={mutation.isPending}>
    {mutation.isPending ? "Deleting..." : "Delete"}
  </button>;
}

useMutation — для CUD-операцій (Create, Update, Delete).

Ключові callback-и:

  • onMutate — до виклику API (optimistic update);
  • onSuccess — після успіху (invalidate);
  • onError — при помилці (rollback);
  • onSettled — після будь-якого результату.

invalidateQueries — позначає кеш як stale → автоматичний refetch.

Optimistic update — оновлюємо кеш до відповіді сервера, відкочуємо при error.

TanStack Query — pagination

function ProductList() {
  const [page, setPage] = useState(1);

  const { data, isPending, isPlaceholderData } =
    useQuery({
      queryKey: ["products", { page }],
      queryFn: () => productsApi.list(page),
      keepPreviousData: true,
      placeholderData: keepPreviousData,
    });

  return (
    <>
      <ul>
        {data?.items.map(p => (
          <li key={p.id}>
            {p.name}
          </li>
        ))}
      </ul>
      <button
        onClick={() => setPage(p => p - 1)}
        disabled={page === 1}
      >Prev</button>
      <button
        onClick={() => setPage(p => p + 1)}
        disabled={isPlaceholderData}
      >Next</button>
    </>
  );
}

Pagination — page в queryKey.

keepPreviousData — при зміні сторінки показуємо старі дані, поки нові вантажаться (немає «мерцання» списку).

isPlaceholderData — true, коли показуються старі дані (для disabled кнопок).

Infinite scroll — useInfiniteQuery:

  • автоматичний fetch наступної сторінки;
  • hasNextPage, fetchNextPage;
  • ідеально для стрічок (feed).

TanStack Query — setup

// main.tsx — setup QueryClient
import {
  QueryClient, QueryClientProvider
} from "@tanstack/react-query";
import { ReactQueryDevtools } from
  "@tanstack/react-query-devtools";

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 60 * 1000,      // 1 min
      retry: 3,
      refetchOnWindowFocus: true,
    },
  },
});

ReactDOM.createRoot(document.getElementById("root")!)
  .render(
    <QueryClientProvider client={queryClient}>
      <App />
      <ReactQueryDevtools />  // dev only
    </QueryClientProvider>
  );

QueryClient — глобальний кеш-менеджер.

Default options:

  • staleTime — скільки дані «свіжі» (без refetch);
  • retry — кількість спроб при error;
  • refetchOnWindowFocus — refetch при поверненні на вкладку;
  • gcTime — скільки кеш живе після відписки (default 5 хв).

DevTools — візуальний інспектор всіх queries (кеш, статус, timeline).

Встановлення:
npm install @tanstack/react-query @tanstack/react-query-devtools

Zustand + TanStack Query — разом

Найкраща практика — використовувати обидва інструменти разом, кожен для свого типу стану:

  • Zustand — client state (theme, UI, cart draft, sidebar open, filters not in URL);
  • TanStack Query — server state (users, products, orders, everything from API);
  • useState — локальний short-lived state (form input, modal toggle);
  • URL (router) — shareable state (page, filter, sort, tab).

Не змішувати: не зберігай server дані в Zustand. Zustand лише для client-only state.

Auth state — може бути в Zustand (user, isAuthenticated), але token в localStorage/cookie.

Performance Techniques

React Performance — що оптимізувати

React.memo, useMemo, useCallback

// React.memo
// Skip re-render if props
// are shallow-equal
const Item = memo(
  ({ id, name }) => (
    <li>{name}</li>
  )
)
// for components
// useMemo
// Cache computed value
// recalc only if deps change
const sorted = useMemo(
  () => items
    .sort(...),
  [items]
)
// for expensive calc
// useCallback
// Stable function reference
// (for memo children)
const handleClick =
  useCallback((id) => {
    deleteItem(id)
  }, [deleteItem])

// for callbacks passed

Як вони працюють разом:

  • Parent renders → new function created → memo(Item) sees new prop → re-renders anyway
  • Fix: useCallback(fn, deps) → same ref → memo(Item) skips → no re-render
  • ⚠️ Don't wrap everything — memo/useMemo/useCallback have their own cost
  • Use only when profiling shows a real bottleneck (large lists, expensive renders)
  • React 19: React Compiler may auto-optimize many of these cases in the future

React.memo — приклад

// Без memo — re-renders on every parent render
function ListItem({ item, onDelete }) {
  return <li>
    {item.name}
    <button onClick={() => onDelete(item.id)}>X</button>
  </li>;
}

// З memo — skip if props unchanged
import { memo } from "react";

const ListItem = memo(function ListItem({
  item, onDelete
}: { item: Item; onDelete: (id: string) => void }) {
  return <li>
    {item.name}
    <button onClick={() => onDelete(item.id)}>X</button>
  </li>;
});

// Custom comparison (if needed)
const ListItem = memo(Component, (prev, next) => {
  return prev.item.id === next.item.id
    && prev.item.name === next.item.name;
});

React.memo — HOC, що пропускає re-render, якщо props shallow-equal.

Коли використовувати:

  • Списки з багатьох елементів (Item в .map);
  • Компоненти з дорогим рендером;
  • Компоненти, що часто отримують однакові props.

Коли НЕ використовувати:

  • Прості компоненти (memo сам має cost);
  • Якщо props завжди нові (об'єкти, функції без useCallback);
  • Дерево й так легке.

Custom compare — для глибокого порівняння (повільніше, але точніше).

useMemo та useCallback — коли потрібні

// useMemo — cache expensive calc
function ProductGrid({ products, query }) {
  const filtered = useMemo(
    () => products
      .filter(p => p.name.includes(query))
      .sort((a, b) => a.name.localeCompare(b.name)),
    [products, query]
  );
  return <ul>{filtered.map(...)}</ul>;
}

// useCallback — stable function for memo child
function UserList({ users }) {
  const handleDelete = useCallback(
    (id: string) => usersApi.delete(id),
    []
  );

  return users.map(u => (
    <ListItem
      key={u.id}
      item={u}
      onDelete={handleDelete}
    />
  ));
}

useMemo — кешує значення.

useCallback — кешує функцію (еквівалент useMemo(() => fn, deps)).

Коли useMemo:

  • Дорогі обчислення (sort, filter, map великих масивів);
  • Об'єкт/масив, що передається в memo-компонент.

Коли useCallback:

  • Функція передається в memo-компонент (щоб props не змінювались);
  • Функція — dep в useEffect.

React 19: React Compiler автоматично оптимізує багато з цих випадків.

List Virtualization — render only visible

Virtualization — приклад (react-window)

import { FixedSizeList as List }
  from "react-window";

function BigList({ items }: {
  items: Item[]
}) {
  const Row = ({ index, style }) => (
    <div style={style}>
      {items[index].name}
    </div>
  );

  return (
    <List
      height={600}
      width={"100%"}
      itemCount={items.length}
      itemSize={50}
    >
      {Row}
    </List>
  );
}

// 10,000 items → only ~12 rows in DOM
// scroll is butter-smooth

react-window — бібліотека для virtualization списків.

Принцип: рендерить лише видимі елементи + невеликий буфер. Решта — порожній простір з scroll.

Переваги:

  • DOM: 12 nodes замість 10,000;
  • Швидкий scroll;
  • Мала пам'ять;
  • Працює з 100k+ елементів.

Альтернативи: @tanstack/react-virtual, react-virtuoso.

Коли: списки > 100 елементів, таблиці, feed.

Transition та useDeferredValue

// useTransition — mark update as non-urgent
import { useTransition } from "react";

function Search() {
  const [query, setQuery] = useState("");
  const [isPending, startTransition] =
    useTransition();

  const onChange = (e) => {
    setQuery(e.target.value); // urgent (input)
    startTransition(() => {
      setResults(filter(e.target.value)); // non-urgent
    });
  };

  return <>
    <input value={query} onChange={onChange} />
    {isPending && <Spinner />}
    <List items={results} />
  </>;

// useDeferredValue — defer a value
const deferredQuery = useDeferredValue(query);
// results use deferredQuery, input uses query

Concurrent React (React 18+) — пріоритезация оновлень.

useTransition — позначає оновлення як non-urgent (може перерватись).

use case: input швидко оновлюється, важкий список — в фоні.

useDeferredValue — «відкладене» значення для дорогих обчислень.

Переваги:

  • Input залишається responsive;
  • Список оновлюється без блокування;
  • isPending — показати spinner;
  • Без Web Worker чи debounce hack.

React Profiler — як знайти вузькі місця

React DevTools Profiler — запис рендерів, показує що, чому і скільки рендерилось.

  • Record — почати запис дій користувача;
  • Flamegraph — час рендеру кожного компонента;
  • Ranked — компоненти, відсортовані за часом;
  • Component — props/state на кожному рендері;
  • Why did this render? — причина (props change, state, parent).

Що шукати:

  • Компоненти, що рендеряться занадто часто;
  • Рендери, де props не змінилися (→ React.memo);
  • Дорогі обчислення на кожному рендері (→ useMemo);
  • Списки, що рендеряться повністю (→ virtualization).

Правило: Measure first, optimize second. Не оптимізуй те, що не є проблемою.

Testing React — огляд

В testing React використовують:

  • Vitest / Jest — test runner;
  • React Testing Library — render + interact з компонентами (render(), screen, fireEvent, userEvent);
  • MSW (Mock Service Worker) — mock API-запитів;
  • Playwright / Cypress — E2E тести (реальний браузер).

Принцип Testing Library: test як користувач взаємодіє з UI, а не як компонент реалізований.

Що тестувати: behavior, не implementation.

React 19: act() більше не потрібен для більшості випадків.

Підсумок

  • useState → Context → Zustand → Redux Toolkit — еволюція state management. Context обмежений (re-render all), Zustand — селективна підписка + middleware.
  • Zustand — ~1KB, без Provider, selectors, persist + devtools middleware, async actions, slices патерн.
  • Client state (UI, theme, cart) vs Server state (API data) — різні інструменти для різних потреб.
  • TanStack Query — cache, dedup, refetch on focus, invalidation, optimistic, pagination, DevTools. Замінює ручний useEffect + fetch.
  • useQuery — читання, useMutation — зміна + invalidate.
  • Performance: React.memo (skip re-render), useMemo (cache calc), useCallback (stable fn), virtualization (big lists), lazy loading, code splitting.
  • Concurrent React: useTransition, useDeferredValue — пріоритезация оновлень.
  • Profile first — React DevTools Profiler. Не оптимізуй гіпотетичне.
  • React 19 — React Compiler автоматизує багато оптимізацій.
