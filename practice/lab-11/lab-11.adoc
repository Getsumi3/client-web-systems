= Лабораторна робота №11

*Тема:* React Router, форми, валідація та автентифікація.

*Мета:* навчитися будувати багатосторінкову SPA-структуру на основі React Router, працювати з route params і query params, створювати форми, виконувати валідацію та реалізовувати простий захищений доступ.

Лабораторна є продовженням **Study Planner**.

== Вимоги до звіту

. Використовувати React та TypeScript.
. Використати React Router.
. Реалізувати щонайменше одну динамічну адресу з route params.
. Використати query params для фільтрації або сортування.
. Реалізувати окремі сторінки/маршрути для основних частин застосунку.
. Реалізувати форму з React Hook Form.
. Реалізувати схему валідації за допомогою Zod.
. Реалізувати просту автентифікацію та захищений маршрут.
. Стан автентифікації зберігати через Auth Context.
. Не використовувати `alert`.
. Дотримуватися ESLint, TypeScript та Conventional Commits.

== Практична частина

=== 1. Структура маршрутів

Розширити Study Planner такими маршрутами:

[source]
----
/
├── /tasks
├── /tasks/:taskId
├── /about
├── /login
└── /profile
----

Маршрут `/tasks/:taskId` повинен відкривати детальну інформацію про конкретне завдання.

Маршрут `/` може перенаправляти на `/tasks`.

=== 2. Layout

Створити спільний layout застосунку з:

* Header;
* навігацією;
* основною областю контенту.

Навігація не повинна повністю перезавантажувати сторінку.

=== 3. Route Params

На сторінці деталей отримувати `taskId` з URL.

Наприклад:

----
/tasks/42
----

На сторінці показати:

* назву;
* опис;
* категорію;
* пріоритет;
* стан виконання.

=== 4. Query Params

Фільтр Study Planner перенести у URL.

Приклад:

----
/tasks?status=completed&priority=high
----

Після оновлення сторінки параметри повинні зберігатися.

Не потрібно зберігати ті самі значення одночасно у двох незалежних state без необхідності.

=== 5. Форма авторизації

Створити сторінку `Login`.

Поля:

* email;
* password.

Використати React Hook Form.

Реалізувати Zod-схему:

* email — обов'язковий та коректного формату;
* password — обов'язковий, мінімум 6 символів.

Помилки повинні показуватися біля відповідних полів.

=== 6. Auth Context

Створити `AuthContext`, який зберігатиме:

* поточного користувача;
* ознаку авторизації;
* функцію login;
* функцію logout.

Для навчальної роботи дозволено реалізувати спрощену автентифікацію без реального сервера.
Наприклад, можна перевіряти тестового користувача або отримувати тестовий token від навчального API.

=== 7. Protected Route

Маршрут `/profile` зробити доступним лише авторизованому користувачу.

Неавторизований користувач повинен автоматично перенаправлятися на `/login`.

Після успішного входу необхідно повернути користувача на сторінку, з якої він прийшов, якщо така сторінка була.

=== 8. Profile

На `/profile` показати:

* email користувача;
* статус авторизації;
* кнопку Logout.

Після Logout захищені сторінки повинні знову стати недоступними.

=== 9. Додаткові завдання

. Додати реєстрацію.
. Реалізувати окремий `NotFound` для маршруту 404.
. Додати nested routes.
. Додати роль `admin` та адміністративний маршрут.
. Зробити lazy loading для однієї сторінки.
. Зберігати token у storage та відновлювати сесію після перезавантаження.
