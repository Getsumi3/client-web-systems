= Лабораторна робота №11

*Тема:* React Router 8, форми, валідація та автентифікація.

*Мета:* навчитися будувати багатосторінкову SPA-структуру на основі React Router, працювати з route params і query params, створювати повторно використовувану форму в діалоговому вікні, організовувати authentication та authorization для дій із даними.

Лабораторна є продовженням **Study Planner**.
Потрібно зберегти попередній REST/API-функціонал і додати навігацію та автентифікацію.

. Реалізувати Auth Context.
. Реалізувати login, logout та protected route.

. Створення, редагування та видалення завдань повинні бути доступні лише авторизованому користувачу.

== Практична частина

=== Версії та встановлення React Router

Для цієї лабораторної використовується **React Router 8**.
У React Router 8 пакет `react-router-dom` більше не використовується: основні API імпортуються з `react-router`, а DOM-специфічний `RouterProvider` — з `react-router/dom`.

Встановити:

[source,bash]
----
npm install react-router
----

Для базової частини лабораторної використовувати Declarative Mode з `BrowserRouter`, `Routes` та `Route`.
Data Router з `createBrowserRouter`, `loader` та `redirect` можна використати як додатковий варіант.

Приклад базового імпорту:

[source,typescript]
----
import {
  BrowserRouter,
  Routes,
  Route,
  Link,
} from 'react-router';
----

Не використовувати приклади з `react-router-dom`, розраховані на старі версії React Router.

=== Стилізація та BEM

Для стилізації обрати один із трьох підходів:

. **SCSS + BEM** — власні стилі з класами за схемою Block__Element--Modifier;
. **Bootstrap** — готові utility та component класи;
. **Tailwind CSS** — utility-first класи.

Не потрібно поєднувати всі три підходи одночасно.

Якщо обрано **SCSS + BEM**:

* стилі організувати за компонентами або логічними блоками;
* кожен компонент або логічний UI-блок має власний `.scss` файл поруч із відповідним компонентом;
* не зберігати стилі компонентів у загальному `App.css` або іншому великому спільному файлі;
* назви класів повинні відповідати BEM;
* не прив'язувати стилі до глибокої структури DOM;
* глобальні стилі залишати лише для справді глобальних речей: `body`, базові стилі, шрифти, reset тощо.

=== 1. Структура маршрутів

Розширити Study Planner такими маршрутами:

[source]
----
/
├── /tasks
├── /tasks/:taskId
├── /login
└── /profile
----

Маршрут `/` може перенаправляти на `/tasks`.

=== 2. Layout та навігація

Створити спільний layout застосунку з:

* Header;
* навігацією;
* основною областю контенту.

Навігація між сторінками повинна працювати без повного перезавантаження браузера.

У навігації передбачити посилання на:

* Tasks;
* Profile;
* Login/Logout відповідно до стану сесії.

=== 3. Route Params та сторінка деталей

На сторінці деталей отримувати `taskId` з URL.

Приклад:

----
/tasks/42
----

Для отримання даних використати repository з лабораторної №10.

На сторінці показати щонайменше:

* назву;
* опис;
* категорію;
* пріоритет;
* стан виконання;
* хто створив завдання;
* дату створення.

Поля `createdBy` та `createdAt` повинні належати domain-моделі `Task`.
Якщо обраний API не надає ці поля, вони можуть бути client-owned metadata. У такому разі потрібно явно позначити їх у коді як дані, якими володіє клієнт, а не сервер.

=== 4. Query Params

Фільтр Study Planner перенести у URL.

Приклад:

----
/tasks?status=completed&priority=high
----

Після оновлення сторінки параметри повинні зберігатися.

Один і той самий фільтр не потрібно одночасно дублювати в незалежному state та URL без чіткої причини.

=== 5. TaskFormDialog — створення та редагування

Створити один повторно використовуваний компонент `TaskFormDialog`, який використовується для двох сценаріїв:

* **create** — відкривається кнопкою `+` на сторінці `/tasks`;
* **edit** — відкривається кнопкою «Редагувати» на сторінці `/tasks/:taskId`.

Не потрібно створювати окремі `CreateTaskForm` та `EditTaskForm`.
Одна форма повинна працювати в двох режимах, отримуючи через props режим та початкові дані.

Приблизний API компонента:

[source,typescript]
----
type TaskFormDialogProps = {
  open: boolean;
  mode: "create" | "edit";
  task?: Task;
  onClose: () => void;
  onSubmit: (data: TaskFormData) => Promise<void>;
};
----

Форма повинна містити:

* назву;
* опис;
* категорію;
* пріоритет.

Використати React Hook Form та Zod.
Під час відправлення показувати pending state та блокувати кнопку Submit.

Після успішного create/edit:

* закрити dialog;
* оновити дані в UI без повного перезавантаження сторінки;
* показати короткий success state.

Dialog повинен коректно закриватися через кнопку Close/Cancel.
Обов'язково передбачити базову доступність: зрозумілий заголовок, keyboard focus та закриття через Escape.

=== 6. Authorization для CRUD-дій

Перегляд списку та деталей завдання можна залишити доступним без авторизації.

Для неавторизованого користувача такі дії повинні бути недоступними:

* створення нового завдання;
* редагування;
* видалення.

Приклад сценарію:

----
Гість → /tasks → /tasks/42 → «Редагувати» → Login
Авторизований → /tasks → «+» → TaskFormDialog → create
----

Не потрібно покладатися лише на приховування кнопок.
Перед виконанням захищеної дії потрібно перевіряти стан авторизації.

Для редагування та видалення після перевірки auth виконати відповідну repository-операцію з Authorization header.
=== 7. Форма Login

Створити сторінку `Login`.

Для рекомендованого DummyJSON використовувати поля:

* username;
* password.

Використати React Hook Form та Zod.

Мінімальна схема:

* username — обов'язковий;
* password — обов'язковий, щонайменше 6 символів у межах цієї лабораторної.

Помилки повинні показуватися біля відповідних полів.

Після коректної відправки форми виконати login-flow.

=== 8. Auth Context та token

Створити `AuthContext`, який зберігатиме щонайменше:

* поточного користувача;
* `accessToken` або ознаку активної сесії;
* `isAuthenticated`;
* `login`;
* `logout`.

Для рекомендованого DummyJSON використовувати реальний authentication flow:

[source,http]
----
POST https://dummyjson.com/auth/login
----

Тіло запиту:

[source,json]
----
{
  "username": "emilys",
  "password": "emilyspass"
}
----

DummyJSON повертає `accessToken` і `refreshToken`.

Для отримання поточного користувача:

[source,http]
----
GET https://dummyjson.com/auth/me
Authorization: Bearer <accessToken>
----

Для базової частини достатньо login, logout, Auth Context та protected route.
Refresh token flow належить до додаткових завдань.

Authentication відповідає на питання «хто користувач?», а authorization — «які дії йому дозволені?». У цій лабораторній authorization демонструється через create/edit/delete для завдань.

Вимога щодо мінімальної довжини пароля тут є лише навчальною перевіркою форми, а не універсальним правилом безпеки.

Для альтернативного API студент адаптує API client/repository до його контракту.

==== API, що використовується в роботі

Рекомендований DummyJSON надає:

[cols="1,2,3",options="header"]
|===
|Метод |Endpoint |Призначення

|POST |`/auth/login` |логін та отримання `accessToken` і `refreshToken`;
|GET |`/auth/me` |отримання поточного авторизованого користувача;
|POST |`/auth/refresh` |оновлення токенів.
|===

Тестові облікові дані для базової роботи: `emilys` / `emilyspass`.
Не потрібно зберігати реальні персональні дані або секрети в репозиторії.
=== 9. Protected Route

Маршрут `/profile` зробити доступним лише авторизованому користувачу.

Неавторизований користувач повинен перенаправлятися на `/login`.

Після успішного входу користувач повинен отримати доступ до protected route.

=== 10. Авторизовані API-запити

Для запитів, що потребують автентифікації, передавати token через заголовок:

[source,http]
----
Authorization: Bearer <token>
----

Ця логіка повинна бути зосереджена в API client або іншому спільному модулі, а не дублюватися в кожному компоненті.

=== 11. Profile та Logout

На `/profile` показати:

* username або email користувача;
* статус авторизації;
* кнопку Logout.

Після Logout protected routes повинні знову стати недоступними.

== Демонстрація на захисті

За час захисту необхідно продемонструвати:

. список `/tasks` та відкриття `/tasks/:taskId`;
. відкриття `TaskFormDialog` через `+` для створення;
. відкриття того самого dialog для редагування з Task Details;
. Login з помилкою Zod-валідації та успішним входом;
. спробу захищеної дії без авторизації та перехід на Login;
. виконання create/edit/delete після авторизації;
. Logout і повторну перевірку захищеної дії.

У коді достатньо коротко показати `AuthContext`, `TaskFormDialog` та місце, де формується Authorization header.

Не потрібно демонструвати всі додаткові можливості.
