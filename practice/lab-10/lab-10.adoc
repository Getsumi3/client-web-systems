= Лабораторна робота №10

*Тема:* React та REST API: асинхронні операції, loading/error/empty states та CRUD.

*Мета:* навчитися інтегрувати React-застосунок із REST API.
Опанувати розділення API-логіки та UI, асинхронні запити, стани завантаження й помилки та операції CRUD.

Лабораторна є продовженням **Study Planner** з попередніх робіт.

== Вимоги до звіту

. Використовувати React та TypeScript.
. Роботу з HTTP винести в окремий API/service layer.
. Реалізувати GET, POST, PATCH/PUT та DELETE.
. Для кожної асинхронної операції передбачити стани loading, success та error.
. Реалізувати empty state для порожнього списку.
. Використати `fetch` або Axios.
. Не дублювати HTTP-запити безпосередньо в UI-компонентах.
. Не використовувати `alert`.
. Дотримуватися ESLint, TypeScript та Conventional Commits.

== Теоретична частина

Опрацювати:

. https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API[Fetch API].
. https://developer.mozilla.org/en-US/docs/Web/API/AbortController[AbortController].
. https://axios-http.com/docs/intro[Axios].
. Матеріали лекції щодо React + REST API, asynchronous state та CRUD.

== Практична частина

=== 1. Підключення API

Замінити локальне джерело даних Study Planner на REST API.

Для лабораторної роботи дозволено використати навчальний API, який підтримує роботу з todo/task-подібними даними, наприклад DummyJSON.

API URL, endpoint-и та їх формати необхідно зберігати централізовано.

==== Важливе уточнення щодо навчального API

API використовується як навчальне джерело даних.
Якщо обраний API не зберігає зміни постійно, це не є помилкою студента.
Необхідно реалізувати коректний CRUD-флоу на стороні клієнта та актуалізацію UI після успішних операцій.
Не потрібно створювати власний backend для цієї лабораторної роботи.

=== 2. API layer

Створити окремий модуль, наприклад:

[source]
----
src/
├── api/
│   ├── client.ts
│   └── tasks.ts
----

У `tasks.ts` реалізувати функції:

* `getTasks()`;
* `createTask(task)`;
* `updateTask(id, task)`;
* `deleteTask(id)`.

UI-компоненти не повинні напряму викликати `fetch` або Axios для роботи із завданнями.

=== 3. Завантаження списку

При відкритті Study Planner:

. показати loading state;
. виконати GET-запит;
. відобразити отримані задачі;
. у разі помилки показати зрозуміле повідомлення.

Необхідно передбачити кнопку повторної спроби.

=== 4. Стани loading, error та empty

Реалізувати окремі візуальні стани:

[source]
----
Loading...
Помилка завантаження. [Спробувати ще]
Завдань не знайдено.
----

Для порожнього результату не показувати порожню таблицю без пояснення.

=== 5. Створення завдання

Форма з лабораторної №8 повинна створювати нове завдання через POST-запит.

Після успішного створення:

. оновити інтерфейс;
. очистити форму;
. показати коротке повідомлення про успіх.

Не потрібно перезавантажувати сторінку.

=== 6. Оновлення та видалення

Для існуючого завдання реалізувати:

* перемикання completed;
* редагування назви або опису;
* видалення.

Після операції UI повинен показувати актуальний стан.

Для видалення додати підтвердження в інтерфейсі або простий confirmation-компонент.

=== 7. Архітектура стану

Розділити:

* server state — дані, отримані від API;
* client/UI state — фільтр, відкриття форми, вибраний елемент тощо.

Не дублювати один і той самий server state без потреби.

=== 8. Додаткові завдання

. Реалізувати `AbortController` для скасування попереднього запиту.
. Додати debounce для пошуку.
. Реалізувати пагінацію.
. Реалізувати optimistic update для зміни completed.
. Додати Axios instance з базовим URL.
. Додати централізовану обробку помилок.
. Додати retry для помилок GET-запиту.

== Демонстрація на захисті

За час захисту необхідно продемонструвати:

. завантаження списку із REST API;
. створення нового завдання;
. одну операцію оновлення або видалення;
. loading/error/empty state або окремий API layer у коді.

Не потрібно демонструвати всі додаткові можливості.
