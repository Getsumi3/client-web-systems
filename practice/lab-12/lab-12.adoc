= Лабораторна робота №12

*Тема:* Підсумковий mini-project: modern React, API, server/client state та архітектура застосунку.

*Мета:* самостійно застосувати знання, отримані під час курсу React, та побудувати невеликий завершений SPA-застосунок.
Продемонструвати вміння розділяти server state та client/UI state, організовувати маршрути, API, repository, форми та повторно використовувані компоненти.

Ця лабораторна є підсумковою.
На відміну від робіт №8–11, предметну область студент обирає самостійно із запропонованих варіантів.

== Вимоги до звіту

. Використовувати React 19.x та Node.js 22.22 або новішу версію.
. Використовувати TypeScript.
. Застосунок повинен бути SPA.
. Використати React Router 8.
. Працювати з REST API або іншим зовнішнім джерелом server state.
. Використати TanStack Query v5 для server state.
. Використати Zustand v5 для client/UI state.
. Використати React Hook Form та Zod щонайменше для однієї форми.
. Організувати код у зрозумілій структурі за одним із підходів: **feature-first** або **type-first**.
. Реалізувати **Repository** для роботи з основною server-side сутністю.
. Створити щонайменше один повторно використовуваний UI-компонент і використати його щонайменше у двох місцях.
. Передбачити loading, error, empty та success states для асинхронних сценаріїв.
. Реалізувати щонайменше одну значущу CRUD-операцію.
. Не використовувати `alert`.
. Для стилізації використати один із підходів: SCSS із дотриманням BEM, Bootstrap або Tailwind CSS.
. Якщо обрано SCSS, дотримуватися BEM-патерну для класів.
. Дотримуватися ESLint та TypeScript.
. Код повинен бути розміщений в особистому GitHub репозиторії студента.
. Дотримуватися Conventional Commits.

== Версії та встановлення основних бібліотек

Для mini-project використовувати актуальний стек курсу:

* React 19.x;
* Node.js 22.22 або новішу версію;
* React Router 8;
* TanStack Query v5;
* Zustand v5;
* React Hook Form + Zod.

Для React Router 8 встановити пакет `react-router`:

[source,bash]
----
npm install react-router
----

Для Declarative Mode імпортувати маршрути з `react-router`, а не з `react-router-dom`.

Основні бібліотеки можна встановити однією командою:

[source,bash]
----
npm install react-router @tanstack/react-query zustand react-hook-form zod @hookform/resolvers
----

=== Розподіл state

TanStack Query використовується для даних, джерелом яких є сервер, а Zustand — для стану, який належить самому клієнтському застосунку, наприклад кошика, обраного, watchlist, плану подорожі або UI-налаштувань.

Не потрібно дублювати один і той самий server state в обох інструментах.

== Архітектурний підхід

У цій лабораторній **не потрібно реалізовувати повний FSD** і не потрібно дотримуватися конкретних назв папок.

Студент може обрати один із двох підходів:

. **feature-first** — код групується переважно за функціональністю;
. **type-first** — код групується переважно за технічною відповідальністю.

Головне — щоб відповідальність модулів була зрозумілою, а API-доступ не був змішаний з UI-кодом.

Приклад спрощеної feature-first структури:

[source]
----
src/
├── app/
├── pages/
├── features/
└── shared/
----

Приклад спрощеної type-first структури:

[source]
----
src/
├── app/
├── pages/
├── components/
├── hooks/
├── repositories/
├── services/
├── store/
└── types/
----

Це лише орієнтири. Структура може відрізнятися, якщо вона залишається зрозумілою.

Не потрібно створювати окрему папку або шар для кожного типу файлів лише заради шаблону.

=== Repository та API boundary

Repository є обов'язковим.

API-запити та побудова endpoint URL повинні бути винесені за межі page/component-рівня.

Рекомендований напрямок залежностей:

[source]
----
Page / Component
       ↓
Repository
       ↓
API client / HTTP
       ↓
External API
----

Repository повинен надавати зрозумілі операції предметної області, наприклад:

[source,typescript]
----
taskRepository.getList()
taskRepository.getById(id)
taskRepository.create(data)
taskRepository.update(id, data)
taskRepository.remove(id)
----

Конкретні назви та набір методів залежать від обраної предметної області.

Компоненти та сторінки не повинні вручну будувати endpoint URL або дублювати HTTP-код.

== Стилізація та BEM

Для стилізації обрати один із трьох підходів:

. **SCSS + BEM** — власні стилі з класами за схемою Block__Element--Modifier;
. **Bootstrap** — готові utility та component класи;
. **Tailwind CSS** — utility-first класи.

Не потрібно поєднувати всі три підходи одночасно.

Якщо обрано **SCSS + BEM**:

* кожен компонент або логічний UI-блок має власний `.scss` файл поруч із відповідним компонентом;
* не зберігати стилі компонентів у загальному `App.css` або іншому великому спільному файлі;
* дотримуватися єдиного підходу до іменування класів;
* не будувати стилі на глибоких селекторах DOM;
* глобальні стилі залишати лише для справді глобальних речей: `body`, базові стилі, шрифти, reset тощо.

== Варіанти mini-project

Вибрати одну з 10 предметних областей:

. **Mini Shop** — каталог товарів, категорії, пошук, сторінка товару, кошик та обране.
. **Movie Explorer** — каталог фільмів, пошук, жанри, деталі, watchlist та власні оцінки.
. **Book Tracker** — каталог книг, пошук, деталі, статус читання та власна бібліотека.
. **Recipe Planner** — каталог рецептів, фільтри, деталі, обране та план харчування.
. **Travel Planner** — напрямки, пошук, деталі, збережені місця та власний маршрут подорожі.
. **Event Planner** — каталог подій, фільтри, деталі, обране та власні події.
. **Job Board** — список вакансій, пошук, фільтри, деталі, збережені вакансії та статус подачі.
. **Workout Planner** — каталог тренувань, фільтри, деталі, власний план та відмітка виконання.
. **Pet Adoption** — каталог тварин, фільтри, деталі, обране та заявки на усиновлення.
. **Expense Tracker** — категорії витрат, список операцій, фільтри, деталі, власний бюджет та аналітика.

Для кожної теми необхідно адаптувати сценарії під її предметну область, а не механічно перейменовувати одну й ту саму реалізацію.

Предметна область може бути змінена за погодженням з викладачем.

== Мінімальний функціонал

Незалежно від обраної теми застосунок повинен містити:

. список основних сутностей;
. пошук або фільтрацію;
. сторінку детального перегляду;
. щонайменше три маршрути;
. створення або редагування однієї сутності;
. видалення або іншу значущу CRUD-операцію;
. окремий client/UI state;
. асинхронний server state;
. щонайменше одну форму з валідацією;
. Repository для роботи з API;
. повторно використовуваний UI-компонент, який використовується в кількох місцях.

Якщо обране зовнішнє API не підтримує потрібну mutation, дозволено реалізувати CRUD для власної client-owned сутності.
Водночас робота з основним server state все одно повинна проходити через TanStack Query та Repository.

== 1. TanStack Query — server state

Створити `QueryClient`.

Використати щонайменше:

* `useQuery`;
* `useMutation`.

Для mutation передбачити оновлення або інвалідацію пов'язаного query.

Дані API повинні залишатися в TanStack Query.
Не переносити response із API у Zustand лише для того, щоб замінити query cache.

Пошукові параметри, pagination та route params можуть бути частиною query key, якщо вони впливають на результат запиту.

== 2. Zustand — client/UI state

Створити щонайменше один store.

Вибрати стан, який справді належить клієнтському застосунку.

Приклади:

* кошик;
* обране;
* watchlist;
* план подорожі;
* список збережених вакансій;
* локальні налаштування UI.

Похідні значення повинні обчислюватися зі state, а не підтримуватися окремим дубльованим state без потреби.

За бажанням можна використати persistence middleware для client-owned даних.
Не потрібно зберігати в Zustand server state.

== 3. Forms — React Hook Form + Zod

Створити щонайменше одну форму з React Hook Form та Zod.

Форма повинна мати реальну предметну мету, наприклад:

* checkout;
* створення або редагування сутності;
* заявка;
* власна подія;
* запис витрати;
* заявка на усиновлення.

Показати валідацію помилкових даних та успішне відправлення форми.

== 4. Shared UI / reuse

Створити щонайменше один повторно використовуваний UI-компонент і використати його у двох або більше місцях.

Наприклад:

* `Button`;
* `Card`;
* `Modal`;
* `FormField`;
* `StatusBadge`;
* `EmptyState`.

Компонент повинен мати реальне повторне використання, а не існувати лише для виконання формальної вимоги.

== 5. UX-стани

Для асинхронних сценаріїв передбачити:

* loading;
* error;
* empty;
* success;
* disabled state для недоступних операцій.

Стан інтерфейсу не повинен залежати від одного універсального прапорця на кшталт `loading = true` для всіх незалежних операцій.

== 6. Додаткові завдання

Для підвищення оцінки реалізувати один або декілька пунктів:

. pagination або infinite scroll;
. optimistic update;
. lazy routes/code splitting;
. `React.memo`, `useMemo` або `useCallback` там, де є обґрунтована потреба;
. адаптивну верстку;
. темну тему;
. unit/component tests;
. доступність клавіатури та базові ARIA-атрибути;
. prefetch окремих даних;
. persistence для cart/favorites/watchlist або іншого client-owned state;
. додаткову складну domain-specific feature.

Під час захисту за короткий час необхідно продемонструвати:

. роботу маршруту з параметром;
. отримання даних через TanStack Query;
. client/UI state через Zustand;
. одну форму та її Zod-валідацію;

Не потрібно демонструвати всі додаткові можливості.
