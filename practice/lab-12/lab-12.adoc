= Лабораторна робота №12

*Тема:* Підсумковий mini-project: modern React із feature-first architecture, server state та client state.

*Мета:* самостійно застосувати знання, отримані під час курсу React, та побудувати невеликий завершений SPA-застосунок.
Продемонструвати вміння розділяти server state та client state, організовувати маршрути, API, форми та повторно використовувані UI-компоненти.

Ця лабораторна є підсумковою.
На відміну від робіт №8–11, предметну область студент обирає самостійно із запропонованих варіантів.

== Вимоги до звіту

. Використовувати React та TypeScript.
. Застосунок повинен бути SPA.
. Використати React Router.
. Працювати з REST API або іншим зовнішнім джерелом server state.
. Використати TanStack Query для server state.
. Використати Zustand для client/UI state.
. Використати React Hook Form та Zod щонайменше для однієї форми.
. Організувати код у feature-first структурі.
. Створити щонайменше один reusable UI wrapper у `shared/ui`.
. Передбачити loading, error, empty та success states для асинхронних сценаріїв.
. Реалізувати щонайменше одну значущу CRUD-операцію.
. Не використовувати `alert`.
. Для стилізації використати один із підходів: SCSS із дотриманням BEM, Bootstrap або Tailwind CSS.
. Якщо обрано SCSS, дотримуватися BEM-патерну для класів.
. Дотримуватися ESLint та TypeScript.
. Код повинен бути розміщений в особистому GitHub репозиторії студента.
. Дотримуватися Conventional Commits.

== Архітектурний підхід

У цій лабораторній використовується **feature-first architecture**.
Не потрібно реалізовувати повний формальний FSD або створювати складну систему правил імпорту.

Орієнтир:

[source]
----
src/
├── app/
│   ├── App.tsx
│   └── providers/
├── pages/
├── widgets/
├── features/
├── entities/
└── shared/
    ├── ui/
    ├── lib/
    └── types/
----

Призначення рівнів:

* `app` — запуск застосунку, providers та глобальна конфігурація;
* `pages` — сторінки та композиція великих блоків;
* `widgets` — великі UI-блоки сторінки;
* `features` — користувацькі дії та сценарії;
* `entities` — моделі та UI конкретних сутностей;
* `shared` — повторно використовувані UI, утиліти та типи.

Не потрібно переносити кожен файл у окрему папку.
Головне — щоб межі відповідальності були зрозумілими.

== Варіанти mini-project

Вибрати один із варіантів:

. **Mini Shop** — каталог товарів, пошук, категорії, сторінка товару, кошик та обране.
. **Movie Explorer** — каталог фільмів, пошук, фільтри, деталі та watchlist.
. **Game Library** — каталог ігор, жанри, пошук, деталі та список улюблених.
. **Travel Planner** — напрямки, пошук, деталі та власний список подорожей.
. **Pet Adoption** — каталог тварин, фільтри, деталі та заявки на усиновлення.

Предметна область може бути змінена за погодженням з викладачем.

== Мінімальний функціонал

Незалежно від обраної теми застосунок повинен містити:

. список сутностей;
. пошук або фільтрацію;
. сторінку детального перегляду;
. щонайменше три маршрути;
. створення або редагування однієї сутності;
. видалення або іншу значущу CRUD-операцію;

=== Приклад для Mini Shop

Застосунок може мати:

[source]
----
/
├── /products
├── /products/:productId
├── /favorites
├── /cart
└── /checkout
----

**TanStack Query** використати для:

* отримання товарів;
* отримання категорій;
* отримання деталей товару;
* mutations.

**Zustand** використати для:

* кошика;
* обраного;
* локальних налаштувань UI.

**React Hook Form + Zod** використати для форми checkout.

=== 1. TanStack Query — server state

Створити `QueryClient`.

Використати щонайменше:

* `useQuery`;
* `useMutation`.

Для mutation передбачити оновлення або інвалідацію пов'язаного query.

Дані API повинні залишатися в TanStack Query.
Не переносити response із API у Zustand лише для того, щоб замінити query cache.

Пошукові параметри, pagination та route params можуть бути частиною query key, якщо вони впливають на результат запиту.

=== 2. Zustand — client/UI state

Створити щонайменше один store.

Наприклад, для кошика:

* add item;
* remove item;
* change quantity;
* clear cart.

Похідні значення, такі як загальна кількість або сума, повинні обчислюватися зі стану, а не підтримуватися окремим дубльованим state без потреби.

За бажанням можна використати persistence middleware для cart/favorites.
Не потрібно зберігати в Zustand server state.

=== 3. Repository/API boundary

API-запити винести з page/component рівня.

Рекомендовано мати окремий API client або repository для предметної області.
Компонент повинен працювати з функцією рівня data-access, а не будувати URL вручну.

=== 4. Shared UI

Створити щонайменше один wrapper у `shared/ui`, наприклад:

* `Button`;
* `Card`;
* `Modal`;
* `FormField`.

Wrapper повинен мати реальне повторне використання щонайменше у двох місцях.

=== 5. UX-стани

Для асинхронних сценаріїв передбачити:

* loading;
* error;
* empty;
* success;
* disabled state для недоступних операцій.

=== 6. Додаткові завдання

Для підвищення оцінки реалізувати один або декілька пунктів:

. pagination або infinite scroll;
. optimistic update;
. lazy routes/code splitting;
. `React.memo`, `useMemo` або `useCallback` там, де є обґрунтована потреба;
. адаптивну верстку;
. темну тему;
. unit/component tests;
. доступність клавіатури та базові ARIA-атрибути;
. prefetch окремих даних;
. persisted cart/favorites;
. import-boundary lint rule між feature/entity/shared шарами.

== Формат захисту

Під час захисту за короткий час необхідно продемонструвати:

. основний користувацький сценарій;
. роботу маршруту з параметром;
. отримання даних через TanStack Query;
. client state через Zustand;
. одну форму та її Zod-валідацію;
. одну CRUD-операцію;
. структуру `app/pages/widgets/features/entities/shared` та пояснення одного архітектурного рішення.

Не потрібно демонструвати всі додаткові можливості.
